Anti-sèche oral — le harness PMIC

Point tuteur · énergie LLM sur Raspberry Pi 5 · ma partie = la mesure matérielle

Ordre : résultat → pourquoi → comment → limites → suite. Règle d'or : chaque « ça marche » = un chiffre.

1 · Contexte en 20 s (situer ma partie)

RAPL (compteur d'énergie des PC Intel/AMD) n'existe pas sur ARM → aucun outil logiciel ne donne la vraie puissance sur le Pi → la mesure réelle doit venir du matériel : c'est ce que fait mon harness.

Triangulation 3 méthodes : CodeCarbon (estimation) · PMIC onboard = ma brique · prise au mur.

3 · Le harness PMIC MA PARTIE

3.0 — L'idée en une phrase

Le Pi 5 a une puce d'alimentation, le PMIC (Renesas DA9091), qui connaît la tension et le courant de chaque rail (CPU, RAM…). Mon harness l'interroge pendant l'inférence et transforme cette suite de puissances instantanées en une énergie en joules.

⚡ À marteler : le PMIC ne donne pas une énergie, il donne une puissance à l'instant t. Tout le boulot du harness = reconstruire l'énergie (la puissance varie → il faut intégrer dans le temps).

3.1 — Étape 1 : lire le PMIC une fois lire_rails()

  • vcgencmd pmic_read_adc → une ligne par grandeur : VDD_CORE_A current=0.39A / VDD_CORE_V volt=0.75V.
  • Une regex récupère le courant (A) et la tension (V) de chaque rail.
  • Puissance d'un rail : P = V × I ; somme des rails → clé TOTAL.

→ Sortie : un instantané {VDD_CORE: 0,29 W, DDR:…, TOTAL: 1,5 W}.

3.2 — Étape 2 : échantillonner EN PARALLÈLE class MesurePMIC

  • Context manager : with MesurePMIC() as pmic:.
  • À l'entrée : lance un thread de fond (daemon) qui lit le PMIC 5×/s, chaque mesure horodatée (time.perf_counter()).
  • Pendant ce temps, l'inférence tourne sans être ralentie ; à la sortie du with, le thread s'arrête.
Pourquoi un thread ? mesurer PENDANT l'inférence (pas après) sans bloquer le modèle.
Pourquoi un context manager ? le with garantit start/stop propre même si l'inférence plante (__exit__ n'avale pas les exceptions).

3.3 — Étape 3 : calculer l'énergie — intégration TRAPÈZE _calculer()

Énergie = aire sous la courbe puissance(temps), entre 2 échantillons :

E = Σ (P₁ + P₂)/2 × Δt

Sorties : energie_joules (total onboard) · energie_par_rail (VDD_CORE = CPU seul) · puissance_moyenne_w.

Pourquoi trapèze et pas « P_moy × durée » ? le trapèze suit la courbe même si les échantillons ne sont pas parfaitement réguliers (jitter du thread) → intégrale plus juste.
→ C'est energie_par_rail[VDD_CORE] qui donne « CPU ≈ 68 % de l'onboard ».

3.4 — Mode MOCK : développer sans le Pi

Si vcgencmd est absent (sur PC) → fausses valeurs plausibles (idle ~1,5 W + bruit). Les chiffres ne valent rien : c'est pour tester la plomberie (le with, le thread, l'intégration). M'a permis d'écrire tout le harness avant d'avoir le Pi.

3.5 — Branchement dans campaign.py

Les 2 méthodes encapsulées sur la même inférence → comparables ligne par ligne :

tracker.start()                       # méthode 1 : CodeCarbon (estimation)
with MesurePMIC() as pmic:            # méthode 2 : PMIC (mesure réelle)
    sortie = modele(prompt, max_tokens=..., temperature=0)   # temp=0 → déterministe
tracker.stop()
# 1 ligne CSV : joules | joules_pmic | joules_pmic_cpu (VDD_CORE) | w_moyen_pmic

Même requête, en même temps → l'écart CodeCarbon/PMIC est direct : ×1,51 à 16 tok → ×1,04 à 256 tok.

3.5 bis — Le flux complet (schéma)

campaign.py  (l'EXPÉRIENCE : quoi mesurer, combien de fois)
  └─ pour chaque [ modèle × max_tokens × prompt × répétition ] :
       ├─ tracker.start()                  ┐
       ├─ with MesurePMIC() as pmic:       │  les 2 méthodes mesurent
       │     sortie = modele(prompt, …)    │  LA MÊME inférence, en même temps
       ├─ tracker.stop()                   ┘
       └─ 1 ligne CSV : joules (CodeCarbon) | joules_pmic | joules_pmic_cpu | w_moyen
  └─ écrit  data/raw/resultats_Pi5_<date>.csv   ← LES RÉSULTATS

D'où sortent les chiffres :
   joules_pmic / tokens          → ~0,43 J/token
   joules (CC) / joules_pmic     → écart ×1,51 (16 tok) → ×1,04 (256 tok)
La séparation à retenir : pmic.py = l'instrument (il sait mesurer ce qu'on met dans le with, il ne connaît rien aux LLM) ; campaign.py = l'expérience (il décide quoi mesurer, combien de fois, et range les résultats). Le harness est volontairement « bête et réutilisable ».

3.6 — Les limites (à dire MOI-MÊME)

  1. Idle inclus (~1,5 W) : E = inférence + Pi-allumé. Plus la requête est longue, plus l'idle gonfle → biaise la compa entre modèles. Correction : E_nette = E_mesurée − (P_idle × durée) (P_idle via pmic.py --duree 60).
  2. Le PMIC ne voit pas le rail 5 V → sous-estime le total système → d'où la prise au mur.
  3. Échantillonnage 5 Hz = ~20-25 pts sur une inférence de plusieurs s → assez. Réglable (hz=) : ↑ = plus fin mais overhead vcgencmd ; ↓ = trop grossier sur requête courte.

3.7 — Questions probables du tuteur → ma réponse

QuestionRéponse
Pourquoi pas lire un compteur d'énergie ? Le PMIC n'a pas de registre d'énergie, seulement V et I instantanés → c'est à moi d'intégrer.
L'overhead de la mesure ? 1 vcgencmd par lecture ; à 5 Hz négligeable devant une inférence de plusieurs s → c'est pourquoi je ne monte pas le Hz.
Précision ? Onboard fiable et réactive (VDD_CORE suit le DVFS 0,75→0,89 V) ; limite connue = le 5 V, couvert par la prise.
