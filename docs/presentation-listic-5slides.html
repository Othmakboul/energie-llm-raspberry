Mesure énergétique d'un LLM embarqué sur Raspberry Pi

Othmane Makboul & Amine Abidi

Encadrants : Sébastien Monnet, Stephan Plassart — Master, LISTIC

Les modèles de langage (LLM) se déploient désormais sur des plateformes contraintes (edge computing). Sur un Raspberry Pi, la consommation énergétique devient une question centrale.

2 / 5

Problématique

« Quel est le coût énergétique d'une requête sur un LLM embarqué, et quels paramètres d'inférence l'influencent le plus ? »

  • Verrou matériel : le Raspberry Pi n'a pas de compteur d'énergie intégré (pas de RAPL comme sur les CPU x86)
  • → il faut donc estimer ou mesurer indirectement l'énergie
  • Peu d'études analysent finement le coût à l'échelle de la requête sur ce type de matériel
  • Paramètres à explorer : taille du prompt, nombre de tokens générés, quantification, modèle

Protocole statistique

  • Inférence de chauffe (warm-up) écartée
  • Répétitions + médiane (robuste au bruit)
  • Échantillon figé (seed) → reproductible

réf. Georges 2007 ; Hoefler & Belli 2015

3 méthodes d'énergie (sur Pi)

  • Logicielle : CodeCarbon (estimation)
  • Physique : prise connectée (au mur)
  • Matérielle : PMIC du Pi 5 (vcgencmd)

Énergie médiane vs max_tokens

  • L'énergie ≈ linéaire avec les tokens générés : r = 0,99
  • Modèle : E ≈ 10 J + ~1 J / token (coût fixe + coût par token)
  • La taille du prompt est négligeable (vérifié ×3) → c'est la sortie qui domine
  • Médiane > moyenne : un outlier à 322 J biaise la moyenne, pas la médiane
